为什么「排版」值得做成一个技能

在 AI 时代，我越来越相信一个判断：个人能力的价值，不在于你自己用了多少次，而在于能被复制多少次。

公众号写作有一个特别烦人的环节——排版。内容写好了，还要手动调字号、调行距、处理代码块、处理表格，稍不注意保存后就乱了。更麻烦的是，公众号编辑器有一堆"潜规则"：

规则 含义 后果
只认 inline CSS 不能用 <style> 和 class 外部样式表全部失效
禁用 <h1> 标题层级要从 <h2> 开始 标题被降级
禁用 <div> 布局容器不被支持 排版坍塌
禁用脚本与嵌入 <script>/<iframe> 一律删除 交互内容消失
图片走自己的 CDN 外链图片可能丢失 图文不同步
SVG 保存即消失 只有 PNG 能活下来 矢量图白做

这些规则每一条都像一颗暗雷，踩到一次就浪费半小时。这件事完全应该自动化——于是就有了把一个"转换脚本"升级成"发布技能"的想法。

从 starter kit 出发，而不是从零开始

我没有从零写代码。我拿到的 starter kit 已经能跑通最基础的流程：读 Markdown 或 Word → 转 HTML → 消毒 → 加样式 → 输出。

📘 知识 ｜ 什么是拿来主义
拿来主义不是抄，而是"理解 → 改造 → 超越"。先读懂别人做了什么、为什么这么做，再决定保留什么、改什么、加什么。

我保留了它的骨架——read → sanitize → style → clean → output 这条流水线是成熟且正确的；我改造了它的"皮肤"和"肌肉"，让它从一个通用转换器变成有我自己审美和个性的发布工具。

我加了哪些能力

在 starter kit 的基础上，我一共加了九项能力。最有价值的是下面这几个：

主题系统：一条 --theme 切换整篇风格

以前改配色要进代码里一行行改颜色。现在五套主题内置，切换只需要一个参数：

python scripts/convert_to_wechat.py 文章.md 输出.html --theme accent

从科技蓝到落日橙，风格不同，但所有元素的间距、对比度都经过同一套规则约束，不会出现"改了标题忘了正文"的尴尬。

Callout 框：公众号排版的核心元素

公众号文章里那些"知识点 / 注意 / 提示"的彩色框，是我认为最能提升专业感的元素。我把它做成了 Markdown 语法，写起来零成本：

💡 提示 ｜ 这样写就够了
用 > [!NOTE] 开头是知识框，> [!WARNING] 是警告框，> [!TIP] 是提示框，> [!PRACTICE] 是实践框。四选一，写作时顺手就加上了。

自动目录与元数据

长文没有目录，读者会迷路。现在目录从你的标题自动生成，作者、日期、摘要写在文章开头的 front-matter 里，一次定义、处处生效。

⚠️ 注意 ｜ 一个必须避开的坑
公众号不支持页内锚点跳转，所以目录要生成为"纯文字列表"而不是链接，否则点了没反应反而显得不专业。

中文排版：自动补上中英文之间的空格

Python脚本 和 Python 脚本，后者读起来明显更舒服。这个细节我一开始没在意，后来发现它直接决定文章的"高级感"。现在转换器会自动处理，而且只加在字母边界，不会把 第1步 拆成 第 1 步 这种怪样子。

一条命令的完整流水线

把上面所有能力串起来，从"想法"到"成品文章"，其实只需要三步：

  1. 用 Markdown 写内容（可以先用模板起稿）
  2. 跑一条命令转换
  3. 粘贴到公众号编辑器发布

# 从模板新建一篇文章 python scripts/convert_to_wechat.py --new tutorial 新文章.md --author WangChunYan # 转换 + 多格式输出（公众号 HTML / 知乎 Markdown / 纯文本） python scripts/convert_to_wechat.py 新文章.md 输出.html --theme accent --formats all

同一份内容，同时拿到三个版本：公众号、知乎、纯文本。一次写作，多渠道分发，这是我最满意的地方。

用 skill-creator 做技能，我学到了什么

这次开发要求必须用 skill-creator 这个"做技能的技能"。走完 intent → interview → draft → test → iterate 的流程，我有三个很具体的体会：

第一，先定义清楚"输入输出"，再动手。 如果你不能用一句话说清"输入什么、输出什么"，你的技能一定不够好。我的一句话定义是：输入 Markdown/Word，输出 copy-paste ready 的公众号 HTML。

第二，边界情况是测试出来的，不是想出来的。 空文件怎么办、超长文章怎么办、GBK 编码怎么办、SVG 图片怎么办——这些问题在写代码时想不到，在真实数据上一跑就全冒出来了。

第三，eval 要能自动断言，而不是"我看着还行"。 我写了一个回归测试，用程序检查"没有禁用标签、callout 存在、目录存在、页脚存在、中英文空格生效"，六项断言全绿才叫通过。

🔧 实践 ｜ 你也可以试试
挑一件你每周都要重复做两次以上的事，试着把它定义成"输入 X → 输出 Y"。你会发现，大部分重复劳动都能被一条命令接管。

结语

我越来越相信，内容和工具是同一件事的两面。会写内容的人很多，但能把"生产内容的过程"也做成产品的人，才真正拥有了复利。

一个人 + 一个 AI + 一个发布技能，就是一个内容工厂。而这条流水线，今天只是第一步——下一篇文章，我会试着让它更聪明：从大纲直接生成初稿。
